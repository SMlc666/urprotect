# External jump-table support: feasibility and bounded design

**Disposition:** genuine external-table support is a separate cross-image/runtime-owner feature, not the already retained GOT-import negative. The repository has an allowed libc dependency and an accepted libc function-import row, but no evidence of a libc table payload provider. HostContext does not admit an arbitrary provider DSO through the image’s declared dependency graph. The child PRD/design need a provider/ownership contract decision before implementation. This is read-only research: no code, fixture, test, manifest, task status, accepted evidence root, or runtime evidence was changed; the fresh bounded in-image ownership PASS was treated as context and not re-reviewed.

## 1. “External table” means external payload, not an external GOT carrier

**Repository facts.** The child PRD still lists “external-table support” as open and explicitly says the current nearest-negative is an undefined dynamic object/GLOB_DAT/GOT-bound dispatch, not support (`.trellis/tasks/10-06-indirect-control-jump-tables/prd.md:49,53`). The design’s external/runtime-owned policy says to preserve the table and binding and retain runtime ownership evidence, while the table model calls for range, encoding, bounds, targets, and ownership (`design.md:101-129`). Implementation step 11 only says external tables need a separate strategy; it does not define the payload/provider boundary (`implement.md:19-25`).

The existing fixture does **not** contain an external table payload. It declares undefined `urp_external_jump_table` (`native/urprotect-runtime/host_context_external_jump_table_fixture.S:41-43`), acquires its address through ADRP/GOT-LDR (`:6-15`), then reads entries through that pointer. The checker/retained producer facts bind the undefined `STT_OBJECT`, exact `R_AARCH64_GLOB_DAT`, and the writable 8-byte GOT slot at VA `0x1fff8` / file offset `0xfff8`; they record no Source Image table-payload range. The retained undefined symbol has `st_value=0`, `st_size=0` (`implement.md:144-154`; the independent parser is `scripts/check-indirect-control-evidence.py:483-554,557-640,1658-1815`). The GOT slot is therefore the **pointer carrier** that the loader fills, not the table storage or its bytes. `.trellis/spec/backend/quality-guidelines.md:165-178` makes that distinction explicit.

**Interpretation.** For the next positive, “external table support” should mean that the loader-resolved object points to a bounded table payload owned by a separately identified provider image (or other explicit runtime owner), and that the payload’s range/bytes and resolved targets are proven. Proving only the import symbol, relocation, GOT slot, and indexed read would repeat the existing negative’s facts, not promote external payload support.

## 2. Provider admission: libc is allowed; arbitrary provider DSO is not

**Repository facts.** HostContext bounds `DT_NEEDED` to at most two entries and admits one recognized system-libc name, or the exact glibc pair `libc.so.6` + `ld-linux-aarch64.so.1`; other names fail preflight (`native/urprotect-runtime/host_image_validation.c:1534-1541,1765-1800`). `RPATH`/`RUNPATH` are rejected, and auxiliary/filter dependency forms are rejected (`:1561-1571`). The runtime adapter loads the sealed image using `dlopen(..., RTLD_NOW | RTLD_LOCAL)` (`native/urprotect-runtime/host_adapter.c:129-180`). Its two-dependency path also refuses nonempty `LD_LIBRARY_PATH`, `LD_PRELOAD`, and `LD_AUDIT` (`:134-148`). The runtime compatibility note calls this a closed libc singleton/exact glibc pair and rejects arbitrary dependency graphs and payload-controlled search paths (`native/urprotect-runtime/README.md:93-107`).

There is one existing libc-provider observation: the imported `getpid` GLOB_DAT call is an independently retained native AArch64/glibc row (`prd.md:47`; `implement.md:77-94`). It proves that tested function import and current-process glibc identity only; it does not prove a defined libc `STT_OBJECT` whose bytes form a jump table. HostContext’s use of the system loader means an already-global symbol may be found by loader lookup, but the repository does not define or attest an arbitrary preloaded DSO as a stable table provider. The external negative never reaches the HostContext loader: its producer fails before Protected Image publication (`implement.md:145,153-157`).

**Blocked unknown / contract decision.** No provider DSO or suitable exported libc object-table symbol is identified by the child task, the fixtures, or the accepted evidence. Thus: (a) a custom DSO cannot currently be declared as the image’s provider; (b) libc is an allowed dependency family, but whether it exports a suitable table payload is unproven; and (c) reliance on an unspecified process-global DSO is not an admissible provider contract. Before implementation, either identify and pin a compatible existing libc object for the first slice, or explicitly approve a narrowly allowlisted provider DSO and its HostContext dependency/runtime-identity contract. Do not infer a provider from the current imported symbol name.

## 3. Minimum viable bounded positive vertical slice (recommendation)

First choose the provider contract above. Subject to that decision, the narrow positive is one native AArch64/glibc ET_DYN consumer and one explicitly approved provider image, with a four-entry signed-32 relative table and exact target set:

1. **Consumer-side source proof:** bind selected `urp_entry` and the exact index guard/default edge; prove the bounded `[0,3]` index reaches one signed `LDRSW`; bind its base-register chain to one undefined dynamic `STT_OBJECT` row (name, dynsym index, binding/type/visibility/version) and exactly one non-PLT `R_AARCH64_GLOB_DAT` row (symbol index, type, addend, relocation VA). Map the relocation destination to its unique writable file-backed 8-byte GOT slot and independently decode the selected ADRP/LDR to that exact slot. The fixture’s existing byte-derived safe-default requirement remains mandatory.
2. **Provider payload/target proof:** parse the exact provider ELF identified by the contract. Bind its **defined** object symbol and `st_size` to a bounded file-backed read-only PT_LOAD/section range; retain table bytes and per-entry signed decode. Prove the affine base, entry width, lower/upper bound and default, then resolve every target to one exact defined executable provider symbol/range and executable PT_LOAD. A minimal safe fixture makes entries relative to the provider table/base and targets functions in the same provider image, so ASLR preserves the relative values. Do not treat the consumer GOT address as the table range or use out-of-consumer targets as unexplained addresses.
3. **Runtime owner proof:** in source and transformed HostContext runs, bind the consumer’s relocated GOT value to the exact provider object mapping/symbol; record provider SONAME/build-id or file digest and process mapping identity, table VA/range/bytes, and each selected target’s provider symbol identity. Revalidate provider identity and table bytes from the loaded provider, not just producer-supplied JSON or a matching SONAME. This is a runtime-owned/preserved table and target contract, not a fabricated source-image `AddressMap` row.
4. **Selected-only transformation:** transform only the selected consumer entry. Preserve provider bytes/address identities and the GLOB_DAT-owned slot. If code placement changes the selected consumer’s GOT-address producer, re-encode only that selected producer through `Aarch64InstructionEncoder`; leave all unselected consumer code and provider/table storage unchanged. Run all indices and the safe default in source and transformed entry; run an unselected observer using the same provider table as a control. Record exact result/target traces, process and entry statuses, streams, release, and image/runtime hashes. No veneer or runtime target translation is needed when every table target is preserved inside the same provider.
5. **Keep admission narrow:** add one typed table-specific `BR` resolution mode requiring the exact provider object/relocation/GOT/bytes/bounds/target proof. Do not make arbitrary GOT loads, external objects, `BR` or `BLR` a generally admitted indirect call. If a dedicated provider DSO is chosen, its exact allowlist entry, dependency closure, loader resolution identity and rollback behavior are prerequisite HostContext work; do not bypass the dependency contract with an uncontrolled global-scope test setup.

This gives a real positive while limiting support to one provider/encoding/target-ownership/runtime tuple. The repository does not currently identify which allowed provider can supply those bytes; that is the blocker to choosing the exact fixture.

## 4. Snapshot/layout publication is not sufficient as-is

**Current representation.** The semantic model has `External`/`RuntimeOwned` ownership ordinals and rewrite policies, but `SemanticJumpTableExtension` still requires a `SemanticSourceRange TableRange`, entry `SourceRange`s, a source instruction/base, output range, and two selected table-reference producers (`src/UrProtect.Core/SemanticPlanning/SemanticPlanExtensions.cs:35-50,60-84,120-172`). `SemanticTarget.RuntimeBinding` is only a string alongside a single `VirtualAddress`/identity (`SemanticValueModels.cs:52-71`); it cannot prove which provider ELF, object symbol, payload bytes, loader mapping, or provider-owned target each runtime value means. `Aarch64JumpTableResolver` only recognizes the local ADRP/ADD/LDRSW/ADR/ADD/BR family and requires the table range to map to file bytes in the one parsed source `ElfFile` (`Aarch64JumpTableResolver.cs:185-219,255-283`). The current external fixture’s extra GOT-LDR shape is consequently not that family.

At publication, `GenericRehydrationEngine.BuildJumpTableRequests` insists the table range maps through the **consumer source image’s** `LoadMap`, and it derives target/base output bindings from selected-function mappings (`GenericRehydrationEngine.cs:1590-1656`). The layout request and clone contract contain one source range, local entries, local target output bindings, and a physical clone; planner validation currently requires `CopiedAndRetargeted`, signed-32 entries, two selected producers, and ownership `Ambiguous` or `Shared` (`ElfLayoutContracts.cs:364-396`; `ElfLayoutPlanner.cs:2888-2923,3163-3228`). It has no external provider-image range or runtime mapping. These contracts correctly model the accepted local shared-table slice, not a provider-owned object.

**Conclusion/recommendation.** Setting `Ownership=External` or `RuntimeOwned` alone would be an unsafe claim and would still fail the current source-range/layout contract. Add a typed external-table owner extension that binds consumer dynsym/GLOB_DAT/GOT facts, provider identity/dynsym object and range/bytes, target identities/ranges, bounds/affine expression and explicit preserve-runtime policy. Rehydration must independently parse/rebind the consumer and provider facts before publication. Keep provider runtime mappings in a typed runtime binding/evidence domain separate from the local image `AddressMap`; layout evidence should state that the external object is preserved and has no local table clone/entry edits. The canonical snapshot is strict `URP-SPS5` (`SemanticPlanSnapshotCanonicalization.cs:15-17`) and layout evidence is schema 3 (`ElfLayoutContracts.cs:493-507`); adding these serialized facts warrants a deliberate schema evolution, not enum-only reuse or a parallel unvalidated JSON claim.

## 5. Nearest-negative and cross-runtime evidence gates

**Existing nearest-negative (already scoped; not re-reviewed here).** Keep `negative-external-table` as the baseline fail-closed row: exact undefined-object/GLOB_DAT/GOT/instruction binding, actual producer exit 4 and `protected-image-producer` stage, generic promoted-family mismatch diagnostic, and no Protected Image/Native Image/loader publication (`implement.md:140-160`; PRD `:53`). The PRD records a fresh scoped PASS for the **safe default-bounds edge and its checksum-refreshed unsafe-branch regression** only; that PASS does not promote external-table support (`prd.md:53`).

**Recommended nearest negatives for a new positive:** (i) missing/wrong provider dependency or provider identity/version, including a same-SONAME different file; (ii) missing/duplicate/undefined/wrong-type/wrong-size provider object, or object range not wholly file-backed and read-only; (iii) GLOB_DAT symbol-index/type/addend/slot mismatch, duplicate/conflicting slot owner, or GOT instruction chain not reaching that exact slot; (iv) any attempt to use the GOT slot bytes as table entries; (v) wrong table byte, base, width, bounds edge, index clobber, signed overflow, or target not inside the exact provider executable mapping/symbol set; (vi) runtime map/dlsym target inconsistent with the bound provider object; (vii) rehydration/provider-byte tampering or unintended provider/table/observer edits. Each must fail before publication/loader handoff with no partial artifacts, and refreshed-checksum tests must reject the semantic inconsistency rather than merely stale hashes.

**Cross-runtime gate.** The child PRD requires separate glibc, musl and Bionic evidence and says only native glibc rows currently exist (`prd.md:50`; design `:231`). The current imported `getpid` evidence is glibc-only; it cannot stand in for external object-table evidence. For every runtime claimed, retain independent source/transformed HostContext executions and exact runtime/provider mapping identity, provider object/table bytes, all bounded targets/results, process/entry status, streams, release and source/protected/native digests. A libc provider name, export, loader resolution, or table layout must be re-established on each runtime; do not transfer glibc identities or success to musl/Bionic. If a provider cannot be admitted or verified on a lane, keep that lane/feature unpromoted and make the scope explicit.

## 6. Scope clarification before implementation

**Yes.** The PRD correctly leaves external-table support open, but does not say whether it means a provider-owned payload or only a GOT-carried pointer. The design says “preserve external binding” without selecting the allowed provider, how its ELF/range/bytes are authenticated, which address domain owns targets, or whether HostContext may load a dedicated DSO (`design.md:101-129`). Implementation step 11 likewise groups external and runtime-owned tables without a provider contract (`implement.md:23`). Resolve these before code changes:

- define the exact first provider: identified libc object symbol, or a newly approved exact provider DSO (including dependency/path/version/runtime identity policy);
- state that an external payload is distinct from the consumer’s GOT slot and specify how provider object range/bytes/targets are independently bound at rehydration and runtime;
- select the narrow target ownership and transformation rule (recommended: provider-local targets, preserved external table/targets, selected consumer only; no runtime translation);
- define whether the first row is glibc-only observation or a promotion gate requiring all three runtime lanes; retain the parent-owned separate runtime evidence requirement.

Until then, the current safe behavior remains the producer’s fail-closed rejection. No implementation/execution evidence is claimed by this note.
