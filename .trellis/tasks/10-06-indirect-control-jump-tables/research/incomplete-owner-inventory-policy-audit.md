# Incomplete Jump-Table Owner Inventory Audit

Scope: read-only audit of the still-open child PRD criterion at `.trellis/tasks/10-06-indirect-control-jump-tables/prd.md:49`, current implementation/tests, layout/publication checks, and retained runtime evidence. No product files were changed and no tests/CI were run. `python3 ./.trellis/scripts/task.py current --source` returned no current-task pointer; the user-supplied child path was used as the audit scope.

## Verdict

The open PRD sentence is too broad if read as saying there is no implemented behavior at all for incomplete in-image owner inventories. The separate external-provider evidence does not prove ambiguous ownership (as the PRD correctly notes), but direct managed tests do cover a narrow, safe policy for a recognized, bounded, in-image AArch64 signed-32 relative table with an exact selected `ADRP`/`ADD` reference even when the owner inventory is incomplete: classify as `Ambiguous` unless positive additional-owner evidence establishes `Shared`, copy entries into a distinct read-only `PF_R` clone, retarget only the selected consumer, and leave the original table and unselected/unknown consumers alone. This behavior is implemented and managed end-to-end tests cover global/default-visible selected-only evidence and stripped section/relocation metadata.

That does **not** resolve the entire criterion. The evidence inventory remains lower-bound evidence, not an exhaustive consumer inventory; no general “private because no other owner was found” proof exists. The production resolver accepts one compiler-shaped signed-32 relative family, not arbitrary jump tables. The retained native shared-table evidence/checker exercises the known shared fixture (two observed consumers) and explicitly requires `Shared`, so it is not native execution evidence for the `Ambiguous` metadata-missing mutations. The smallest useful next step is to split/restate PRD acceptance: close the narrow, already-tested managed fallback as a scoped subcriterion, while keeping other table families and any demand for native execution of metadata-stripped inputs open. A new implementation for broader behavior first needs product requirements enumerating admitted encodings/owner policies; runtime promotion additionally needs hosted evidence for the relevant runtime rows.

## Existing policy and recognition boundary

- `src/UrProtect.Core/Aarch64Semantics/Aarch64JumpTableResolver.cs:152-179` declares the resolver as the first selected-function, targeted-read family; it does not scan unrelated executable ranges. `:188-228` recognizes the dispatch only when the branch is `BR` and the exact adjacent register/data-flow shape is `ADRP` / immediate `ADD` / indexed `LDRSW` / `ADR` / `ADD` / `BR`. The selected index must survive to dispatch (`:230-269`); the bounds proof is an unsigned `CMP`/`B.HI`, lower bound must be zero, and table count is bounded (`:248-279`).
- The source table must be wholly file-backed through the structural load map and within source bytes (`:288-300`). Each entry is read as signed `int32`; signed target addition must not overflow, and every target must be aligned, executable, and inside the selected function's decoded closure; the default must also be in that closure (`:302-348`). This is not support for arbitrary target sets or out-of-function targets.
- Selected reference relocations, when present, must be nonconflicting and identify the same table object (`:1127-1169`). Missing/incomplete section relocation evidence can fall through to an empty/partial owner-fact set; a malformed or conflicting selected-site relocation fails resolution. Owner collection is deliberately fail-closed as a proof operation: `ResolveOwnerReferences` at `:1172-1286` requires one matching ADRP and ADD object-symbol row for deriving owner facts, maps each candidate to exactly one function, and discards the *entire* owner proof if a candidate's owner section is invalid/mismatched (`:1233-1246`).
- Owner facts in `src/UrProtect.Core/Aarch64Semantics/Aarch64JumpTableResolver.cs:20-41` carry relocation section/`sh_info` target section, owner function section header and range, relocation site/type/addend, exact symbol-table identity and symbol fields, and selected/unselected status. `TryGetValidatedOwnerSection` checks executable, non-`NOBITS`, file-backed section/function/site containment (`:1288-1330+`).
- `HasObservedAdditionalOwner` means positive lower-bound evidence: a non-selected owner has both a matching ADRP and ADD row (`:1280-1285`). It does **not** mean the inventory is exhaustive. `src/UrProtect.Core/SemanticPlanning/Aarch64SemanticPlanFactory.cs:1524-1597` maps the table/entry identities, targets, bounds, producer chain and owner facts to the semantic extension; classification is `Shared` only on that positive observation, otherwise `Ambiguous`, always `CopiedAndRetargeted`, and `ownerInventoryComplete: false` (`:1588-1597`).
- `src/UrProtect.Core/SemanticPlanning/SemanticPlanExtensions.cs:30-136` models `Ambiguous` as a distinct ownership value (ordinal 4), typed per-entry source/target bindings, producer chain, owner-reference rows and inventory completeness. Its comment states the current RELA facts are positive but not exhaustive (`:132-134`). `src/UrProtect.Core/SemanticPlanning/SemanticPlanSnapshotValidation.cs:650-809` validates bounded structure and owner rows; for this implementation it requires signed-32 copied-and-retargeted tables, two selected reference producers, incomplete owner inventory, and rejects `SelectedFunctionPrivate` on this path. It also requires a positive additional-owner pair for `Shared` and forbids downgrading such positive evidence to `Ambiguous` (`:774-808`).

## Publication, layout and materialization are already wired

- Protected-image snapshot validation invokes `ValidateJumpTableOwnerReferences` before accepting a snapshot (`src/UrProtect.Core/Application/Rehydration/GenericRehydrationEngine.cs:415-438`). The validator rechecks every serialized owner row against source section headers, exact linked RELA identity and symbol-table fields, parsed function symbol, section/file bounds and executable `PT_LOAD` mappings (`:587-769`). It bounds aggregate work (`:615-632,771-780`).
- For each table, `ValidateJumpTableSourceContract` requires a structured proof, a selected branch and both producers in exactly one selected region/function, re-decodes the complete selected function from source bytes with AsmStone, compares canonical instruction facts, and calls `Aarch64JumpTableResolver.TryResolve` again (`:803-1012`). `MatchesSourceJumpTable` compares the rederived ownership, all carried producer/owner rows, bounds, entries and default to the snapshot (`:1015-1057+`). A forged/omitted owner row, changed selected producer chain, or selected relocation contradiction therefore does not become accepted owner evidence.
- The `ElfLayoutJumpTableEditRequest`/`ElfLayoutJumpTableClone` carry `Ownership`, `OwnerReferences`, `OwnerInventoryComplete`, requested/output/source ranges, rewrite policy and producer chain (`src/UrProtect.Core/ElfLayout/ElfLayoutContracts.cs:359-396`). Rehydration builds those requests from the validated snapshot (`GenericRehydrationEngine.cs:1799-1818`) and separately fixes the selected producer instructions toward the clone through the instruction encoder (`:1953-2045+`).
- `src/UrProtect.Core/ElfLayout/ElfLayoutPlanner.cs:3163-3229` only admits this copy path for signed 32-bit, scale 1, incomplete inventory, two distinct selected producers, and `Ambiguous` or `Shared` ownership. It creates a distinct clone in the read-only segment and retains source/output mappings (`:720-767`); copied-clone validation requires a distinct file-backed `PF_R` `PT_LOAD`, exact size, two producers and incomplete inventory (`:1170-1213`). `BuildJumpTableEdits` checks source table file mapping and every source entry/target binding before deriving cloned entry edits (`:2878-3045+`).
- `src/UrProtect.Core/ElfLayout/ElfLayoutMaterializer.cs:1680-1777` requires one-to-one clone/binding identities, a distinct read-only mapped clone, preserved original table bytes, and matching source/output maps. Per-entry validation checks ordered unique entry identity/ranges, source bytes vs source targets, output mappings, signed relative target/base arithmetic and edit bytes (`:1780-1905+`). It emits no result bytes on failed post-validation.

## What remains missing, and hazards that must stay fail-closed

1. **No exhaustive inventory/private proof.** `OwnerInventoryComplete` is always false for the supported resolver/layout path. `Shared` is only “at least one additional owner pair positively observed”; absence of a second RELA owner never proves private. Do not treat a global/weak/default-visible symbol, `sh_info` mismatch, omitted relocation rows or section stripping as evidence that unknown references do not exist.
2. **Only one table family.** The resolver admits a narrow zero-based bounded signed-32 LDRSW-relative dispatch. Absolute tables, 8/16/64-bit entries, different scales/addends/bases, multi-instruction or non-adjacent ADRP/ADD producers, other branch forms, wider index/default rules and direct-switch forms are not established. The narrow positive cannot close “general jump-table ownership policy.”
3. **Only in-image selected closure.** Every table target and the default are required in selected closure. No local table route supports remote/unselected target blocks; external/provider ownership must continue through the separate typed provider contracts and cannot be inferred from `RuntimeResolved` or generic `Ambiguous`.
4. **Owner/source facts must not be trusted from snapshots.** Cross-check every carried `sh_info`, owner function section, RELA site, symbol-table identity and selected classification against source; any malformed candidate invalidates the entire owner proof. Re-derive selected producer chain, bounds, target table bytes and target set from source. Missing facts become Ambiguous only when the machine-code table proof itself is exact; conflicting selected evidence fails before publication.
5. **Keep source preservation and clone separation.** Never edit the source table to retarget a selected consumer when unknown users may exist. Preserve the source table and unselected/unknown references, clone only into distinct PF_R, non-W/non-X output, and retarget the exact selected producer chain. Missing `PT_NULL`/layout capacity, source/output range mismatch, incomplete output map, overlap, or unrepresentable signed output displacement must fail before output publication.
6. **Keep strict bounded range and mapping proofs.** Require a single complete source file-backed mapping for table bytes, safe half-open arithmetic, no overflow/truncation/aliasing, unique executable source target mappings, and unique output file-backed clone/target mappings. The independent checker rejects partial/multiple PT_LOAD ownership; do not relax that to a byte-inequality or segment-count heuristic.
7. **Runtime evidence is not feature promotion.** Current runtime checker proves one native shared fixture and its target-selection behavior, not the global-visible or sectionless input variants. Musl/Bionic shared rows still require hosted evidence and remain non-promoted; no runtime success should widen encodings or owner classes.

## Recommendation

No new code is required to establish the narrow managed safe-default for an exact selected ADRP/ADD signed-relative table with incomplete inventory: the behavior is already implemented and has direct positive rehydration coverage plus fail-closed tamper/conflict tests. The smallest useful next action is to split the PRD criterion (without broadening claims):

- **Scoped subcriterion that can be satisfied:** for the recognized bounded in-image signed-32 relative family, exact selected reference + incomplete/absent owner inventory is classified Ambiguous, copied to a distinct PF_R range, only the selected producer is retargeted, source table/unknown consumer bytes remain unchanged, and publication rederives selected and carried owner facts. Cite the tests above and keep `OwnerInventoryComplete=false` explicit.
- **Remain open:** general owner enumeration/private-versus-shared proof, other table encodings/instruction families, fully symbol-less sources, and untested runtime rows. A new code slice should wait for product requirements listing admitted forms and their ownership fallback; a runtime-evidence claim for the ambiguous-mutated inputs needs a dedicated native evidence scenario/checker mode that permits `Ambiguous` and validates no-owner/selected-only facts instead of reusing the hard-coded Shared checker.

A single unsupported-family negative could establish fail-closed rejection for that named shape, but cannot close general support. Do not add a permissive fallback or relabel missing ownership evidence as Shared/Private to satisfy the open wording.
